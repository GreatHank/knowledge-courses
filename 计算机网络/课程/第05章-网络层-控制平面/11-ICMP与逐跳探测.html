IP中的控制消息

ICMP（Internet Control Message Protocol）用来报告网络层差错或提供相关控制信息。以IPv4为例，ICMP报文装在IP数据报中，协议号为1，不需要套一个UDP或TCP首部。它服务于IP通信，通常作为网络层体系的一部分讨论。

类型（Type）给出消息的大类，代码（Code）细分原因。许多差错报文引用触发差错的原IP首部与初始负载，让源端判断是哪次发送出了问题；Echo等消息有自己的格式，不能把“引用原分组”说成所有ICMP消息都具有的统一内容。

IPv4 Type / Code含义本章用途
8 / 0Echo Requestping发送回显请求
0 / 0Echo Reply对方返回回显应答
11 / 0Time Exceeded转发时TTL耗尽
3 / 3Destination Unreachable：端口不可达经典UDP traceroute抵达关闭端口时的终点信号

类型与字段核对见RFC 792。教材图5.19还列出Source Quench（类型4），但它已被RFC 6633弃用，不能作为现行拥塞控制机制来学习。

逐渐增加TTL，让不同位置返回消息

教材的traceroute模型向目的主机发送UDP探测分组，选择通常未开放的高端口，依次把TTL设为1、2、3……。TTL=1的分组在第一台转发路由器耗尽；TTL=2通常到第二台；相应路由器丢弃该分组，并可能向源端返回Time Exceeded。

探测轮次（路径稳定的简化例子）预期响应位置源端观察
TTL=1第一跳路由器响应IP地址与这次探测的往返时间
TTL=2第二跳路由器另一个响应IP地址与往返时间
TTL逐渐增大更远的路由器逐步得到路径上的响应信息
探测抵达目的且UDP端口关闭目的主机端口不可达，表明这类探测已抵达终点

IPv4 ICMP差错报文并不自带路由器的主机名。工具显示名称通常还需另做DNS反向解析；教材PDF456把名称获取归入ICMP，读时需作这一区分。工具也可能采用ICMP或TCP探测，终点响应方式随探测类型变化。

从结果能够推出什么

一行中的RTT包含探测去程、响应回程及处理时间，不是源端到该路由器某一条链路的单独时延。相邻两行RTT相减，也不能可靠地当作它们之间链路的时延：回程可能不同，排队和处理时间也会变化。

没有响应可能来自过滤、限速、回程问题或设备不回复，不能直接断言该跳链路断开。负载分担与路由变化还可能让不同探测经过不同节点。ping收到应答说明该次回显交换成功；未收到应答不单独证明主机已关机。

ICMPv6有独立的消息规范与类型编号，不能把上表的IPv4数字直接套到IPv6。本页解释协议和探测逻辑，没有运行公共网络探测或抓包。
