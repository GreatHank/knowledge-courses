把一跳的时间拆开

分量发生了什么依赖什么
处理 dproc检查首部、决定输出方向等实现与工作量
排队 dqueue等待前面的分组和正在使用的出口到达过程、已有队列与服务速度
传输/发送 dtrans把本包的所有位推入链路L/R
传播 dprop已经进入链路的信号向另一端行进距离 d / 传播速度 s
dnodal = dproc + dqueue + L/R + d/s

教材常称 transmission delay 为传输时延，这里也写“发送时延”以区别传播。它们都以秒计，但一个由包长与链路速率决定，一个由距离与媒介传播速度决定。

第一位可以到达，最后一位还没发出

在理想连续信号模型中，从发送开始计时，第一位前沿经过 d/s 到达另一端，最后一位末尾经过 L/R + d/s 到达。若 d/s < L/R，接收方会在发送方发完之前开始收到这个包；这不违反存储转发，因为下一台路由器还要等整包收齐才转发。

补充算例：L = 12000 bit，R = 10 Mbps，距离 1000 km，传播速度 2 × 108 m/s。发送为 1.2 ms，传播为 5 ms，整包到齐为 6.2 ms。R 升为 100 Mbps 时，发送缩短到 0.12 ms，而传播仍是 5 ms，总计 5.12 ms。

多跳需要累加，条件也要跟着写

教材式 (1.2) 假定有 N 条链路、N−1 台中间路由器；每个发送节点的处理时延相同、链路速率相同、传播时延相同，且排队可忽略：

dend-end = N(dproc + L/R + dprop)

这里 N 包括源发出的第一条链路，不是路由器数量。若各跳不同，补充的一般写法为 ∑i=1…N(dproc,i + dqueue,i + L/Ri + di/si)，仍按本课存储转发的单包模型，且没有另加接收应用处理时间。

应用体验还可能包含音频积攒成包的 packetization delay、共享媒介等待发送的时间，以及应用自身计算。若题目问“点击到看到网页”，仅相加路由器时延通常不够。

Traceroute 观察的是探测往返时间

教材通过多组探测包与路由器回复展示路径及 RTT（round-trip time）。每行测到的是探测发出到该次回复回来之间的时间，包含去程、回复路径、排队与处理；它不是某条链路的单向传播时延。不同探测的排队不同，所以更后面一跳的 RTT 可能反而更小，不能直接逐行相减解释为每跳耗时。

补充实现说明：Windows tracert 递增 TTL，以中间路由器的 ICMP Time Exceeded 和目的端响应定位跳点。星号表示等待时间内没有得到相应响应；不返回响应的路由器也可能显示星号，因此不能只凭星号断言业务分组在该跳丢失。依据 Microsoft 官方说明（2026-10-23）。

本轮未执行 traceroute / tracert。教材中的输出是书中示例，不是用户当前网络的测量结果。
