编码码率、下载吞吐量和缓冲要一起看

视频是连续图像经编码后的数据。编码码率 r 表示每秒播放内容需要多少比特；下载吞吐量 c 表示网络每秒实际取得多少比特。播放缓冲存放已下载但尚未播放的内容，允许下载和播放在一段时间内不同步。

以恒定码率模型为例，2 Mbps 视频播放67分钟需要约2×10⁶×67×60 bit，即约1.005 GB（十进制）。持续播放要求长期供给跟得上消耗，但全程平均吞吐量够大，也不保证每一段都不卡：短时断流可能在之后带宽恢复前就耗尽缓冲。

缓冲变化率 ≈ c − r （以 bit/s 计）

这是补充的恒定码率、连续播放近似。若 c<r 持续存在，有限缓冲只能暂时掩盖差额；提前多缓冲则增加启动等待。真实编码和下载速率会变化。

DASH把选择放到下一段

Dynamic Adaptive Streaming over HTTP（DASH）为同一视频准备多种码率版本，并分成短片段。客户端先取得清单（manifest），知道可用版本及其地址；再结合已测吞吐量和缓冲余量，选择下一段的质量，用 HTTP 请求取得。

读取清单→选下一段码率→下载并测量→更新缓冲与选择

网络变慢时，播放器可选择码率更低的后续片段；已经下载的片段不会因这次选择自动缩小。服务器提供可选内容，客户端执行选择算法；清单本身不是整部视频。具体片段长度与选择策略因实现而异。

CDN同时安排副本与服务位置

把所有视频放在一个远端中心，会重复占用长路径链路，也容易受中心及其连接故障影响。内容分发网络（CDN）把内容副本放到不同位置，再把请求引向合适的服务集群。

部署思路怎样靠近用户维护代价
Enter Deep把较小集群深入接入ISP内部位置多，部署和管理更分散。
Bring Home在较少的互联位置部署较大集群较集中，但到部分用户的路径可能更长。

内容可以提前推送，也可以在未命中时拉取并缓存。靠近用户不只指地理距离：路由、拥塞、可用吞吐量、负载和是否已有副本都会影响体验；解析器所在位置也未必代表用户位置。

DNS参与选址，视频走另一条连接

教材的 NetCinema/KingCDN 示例中，用户取得网页后查询视频域名；内容提供者的 DNS 把名称引到 CDN 域，CDN 的 DNS 再选择内容服务器地址。地址返回客户端后，客户端与内容服务器建立连接并请求视频。

图中的本地 DNS 传递的是名称和地址信息，视频字节不需要通过 DNS 服务器转发。DNS 返回的地址可以影响服务位置，但服务器选择并不只能用 DNS 完成。

把教材案例当作设计比较

教材描述 Netflix 在云端处理登录、目录与内容加工，把多版本视频推入自己的 CDN；客户端拿到服务地址与清单后直接取片段。它用这个案例说明：业务入口和大流量内容传送可以分开，选址可以由应用逻辑直接完成。

教材的 YouTube 案例则用于对比拉取缓存与 DNS 选址。两者帮助理解“如何放副本、如何选服务点、谁控制视频质量”三个独立决定。书中的部署数量、硬件规模及具体播放器行为带有写作年代，本课不将其当作2026年的实现说明。
