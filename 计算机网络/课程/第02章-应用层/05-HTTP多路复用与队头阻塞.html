05 · HTTP多路复用与队头阻塞

把响应拆成帧后，小对象为什么更早完成，哪些阻塞仍然存在？

复用一条连接之后，怎样让小对象不一直等

在本节比较模型中，HTTP/1.1 的一条连接要先交付大对象的完整响应，后面的短响应就会等待。即便流水线已经把请求发出去，响应的顺序约束也仍在。开多条 TCP 连接能分散等待，却增加连接状态，并改变与其他连接竞争瓶颈带宽的方式。

HTTP/2 把消息拆成带有流标识的二进制帧，让不同流的帧在一条 TCP 连接中交错传输。接收端按所属流重新组合消息；帧的交错不意味着把不同响应的内容混成一份。

同样1016帧，小对象的完成时间可以不同

教材设1个大对象需要1000帧，另外8个小对象各需要2帧，并为便于比较假设帧长相同。若大对象在前、响应逐个发送，所有小对象都完成时要等到第1016帧。若每轮先发大对象1帧，再各发8个小对象1帧，则两轮共18帧后，8个小对象已经全部完成。

调度方式最初的发送次序小对象全部完成
逐个完整响应大对象×1000，再发8个小对象第1016帧后
两轮交错示例大1、小1…小8；再重复一轮第18帧后

总数据量仍是1016帧，瓶颈带宽没有增加；改善的是短响应的完成时间。大对象让出了一部分发送机会，所以不能把“所有对象都早完成”作为无条件结论。真实帧可以有不同长度，调度也不必采用这个轮转顺序。

分清应用层等待与 TCP 字节流等待

HTTP/2 消除了本例中“必须先送完整个大响应”的限制。但底层仍是一条有序 TCP 字节流；如果前面的字节丢失，后续已到达字节也可能要等缺口补齐才能向上交付，影响多个 HTTP 流。这是另一个层次的队头阻塞（head-of-line blocking）。

教材还介绍头部压缩、响应优先级和服务器推送。优先级表达服务顺序的偏好，不是带宽保证；服务器推送允许在显式请求前提供相关资源。这里讲的是教材版本中的协议机制，不据此断言某个浏览器当前支持或启用了这些功能。

版本补充：书内146页所说“HTTP/3尚未标准化”属于2020年前后的写作背景。RFC 9114（2022）已经定义 HTTP 在 QUIC 上的映射。不同流不再共用同一条 TCP 字节流；QUIC 仍受网络容量、拥塞与丢包影响。机制细节留到第3章。
