沿一次内容访问串起本章

设用户按网址请求一个视频。这条路径可以串起本章，但其中缓存、CDN与自适应策略是可选设计，不是每次请求都必须经过的固定流程。

  1. 应用进程决定请求内容，按协议组织消息。
  2. 需要时通过 DNS 取得服务地址；已有缓存可能省去部分查询。
  3. 选择相应运输服务，通过 Socket 或更高层库建立通信。
  4. HTTP 请求取得清单或对象；Cookie 可能帮助业务关联会话。
  5. 缓存和 CDN 决定副本从哪里提供；DASH 客户端决定下一片段选哪种码率。
  6. 接收端按消息边界解释字节，并交给播放器或其他业务逻辑。

邮件走的是另一套流程：提交、服务器转交、邮箱访问分担责任。P2P 又改变了文件由谁上传。它们共用网络基础设施，却不共用同一种应用协议。

用几个边界整理机制

容易混在一起的概念本章区分
应用 / 协议应用含界面、存储和业务；协议规定通信消息与动作。
持久连接 / 会话状态前者复用运输连接；后者关联业务请求。
缓存命中 / 304前者可直接使用副本；后者是一次验证响应。
DNS / 内容传送DNS提供名称信息；内容由对应应用连接传送。
P2P下界 / 实际完成时间前者依赖理想资源与调度；后者还受协议和节点行为影响。
字节流 / 应用消息TCP排序字节；应用必须定义消息如何结束。

阅读一个具体实现时，可以沿着“谁保存状态、谁做决定、消息怎样分隔、失败后谁知道”追踪，来分清不同层的职责。
