先看记录类型，再解释它的值

教材把资源记录（resource record，RR）概括成 (Name, Value, Type, TTL)。这是便于理解的模型；Name 和 Value 的含义随 Type 变化。实际报文还包含类别、长度等字段，并非把这个四元组直接写成文本发送。

类型Name / Value的含义教学示例
A主机名 → IPv4地址web.example.com → 192.0.2.10
NS域 → 为它提供权威服务的名称服务器名example.com → ns1.example.com
CNAME别名 → 规范名称www.example.com → web.example.com
MX邮件域 → 邮件接收服务器；数据还含优先值example.com → 10 mail.example.com

A 记录返回地址；NS、CNAME、MX 的目标是名字，通常还需解析该名字的地址。MX 的优先值越小，越优先尝试。表中域名和地址仅作结构示意，没有实际查询这些记录。IPv6 地址对应 AAAA 类型，本章主要沿用 A 记录讲解。

规则补充：不能按教材的简略别名叙述，给同一个名字同时配置 CNAME 和 MX/A 等普通数据。RFC 1034 §3.6.2说明 CNAME 的互斥规则；上表把 www.example.com 的别名与 example.com 的邮件记录分开。

同一种报文框架装查询和回答

首部中的标识符帮助把响应对应到查询；查询/响应标志区分方向。递归期望（RD）、递归可用（RA）与权威回答（AA）表达不同事实，不能把“提供递归服务”理解成“对所有名字都有权威”。四个计数字段说明后面各部分有多少项。

Question 说明问哪个名字、哪种类型；Answer 放回答所需的记录；Authority 可携带进一步联系权威服务器的线索；Additional 放有帮助的额外记录。例如答案给出邮件服务器名时，附加部分可能同时给出地址，减少另一次查询。

回答不总是一条地址：可能有多个 A 记录，可能先给出 CNAME，也可能是转介或不存在的结果。因此阅读 DNS 要先确认查询类型与响应状态，再解释记录，不能只找第一个数字地址。

委派与本区数据要衔接

教材的建站例子分两处维护数据：通过注册流程建立父区到域的委派；在自己的权威服务器中发布主机地址、邮件记录等本区数据。当名称服务器的名字位于被委派域内时，父区提供的地址胶水（glue）可避免“要找这个服务器，必须先问这个服务器”的循环。

只在自己的机器里写一条 A 记录，不会自动让全球解析器知道应到哪里问；只有委派、可达的权威服务与所需记录衔接起来，查询路径才成立。这里解释数据组织，没有注册域名或修改 DNS 配置。

缓存提高效率，也扩大错误答案的影响

拒绝服务攻击会耗尽查询处理或链路资源；伪造响应和缓存投毒则试图让解析器接受错误记录。缓存一旦保存错误数据，后续请求可能重复使用它。

边界补充：DNSSEC（RFC 4033）为 DNS 数据提供来源认证与完整性验证，不加密查询内容，也不消除拒绝服务问题。数据可信、查询保密和服务可用是不同目标。
