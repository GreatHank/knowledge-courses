先安排进程之间的角色

网络应用由运行在不同端系统上的进程协作完成。浏览器进程与 Web 服务进程交换请求和响应；通常无需为这项新应用修改沿途路由器。这里设计的是应用架构：哪些进程提供服务、谁发起通信、状态放在哪里。第1章的分层结构则说明网络怎样提供这些通信服务。

在客户—服务器（client-server）架构中，服务端通常持续在线并提供稳定的联系入口，客户端向它请求服务。“服务器”可以由数据中心中的很多机器共同承担，不必是一台电脑。P2P 架构让对等方（peer）互相服务；加入者增加下载需求，也可能贡献上传能力，但节点随时离开，资源管理和可靠性更难。

客户和服务器还是一次会话中的角色：先联系对方的是客户，等待被联系的是服务器。同一个 P2P 进程可以在一段通信中下载，在另一段通信中上传；角色与硬件型号无关。

地址找到对端，Socket 连接程序与运输服务

Socket（套接字）是程序收发网络数据的接口。应用决定发送什么字节、何时发送、收到后怎么处理；选择 TCP 或 UDP 后，借助操作系统提供的运输服务完成传送。

只有主机地址还不够：同一台机器可能同时运行浏览器、邮件程序和游戏。教材用IP 地址 + 端口号定位目的端的通信入口，例如 HTTP 示例的 TCP 80、服务器间 SMTP 的 TCP 25。教材此处用 IPv4 举例；“IP 地址都是32位”不能推广到 IPv6。TCP 连接还需要双方地址与端口来区分，第3章会展开。

把需求与已有服务分开

需求维度应用关心的问题本章 TCP / UDP 服务边界
可靠交付文件能否完整、按序得到？TCP 提供可靠、有序字节流；UDP 不保证交付、次序和去重。
吞吐量可用速率能否跟上消耗？普通 TCP / UDP 服务都不预留最低吞吐量。
时限晚到的数据还有用吗？两者都不保证在某个期限内到达。
安全内容、身份与完整性怎样保护？裸 TCP / UDP 不提供加密；教材以 TCP 上的 TLS 为例。

文件下载可随可用带宽伸缩，属于弹性应用（elastic application）；交互语音更在意迟到是否影响对话。容忍一些媒体损伤，不等于可无限丢包。视频也能通过缓冲与改变编码码率适应网络，而不要求底层给出硬时限保证。

TCP 建立连接后可以双向传输，并用拥塞控制约束发送速度。可靠服务也有失败边界：连接可能超时或复位，且“运输层已收到”不等于“业务已经处理成功”。UDP 自身没有拥塞控制，不表示应用可以忽略网络拥塞；应用或其上层协议仍需考虑资源使用。TLS 是另外加入的安全机制，不能从“用了 TCP”推断“已经加密”。

协议是一套消息规则

应用层协议要规定消息类型、字段与分隔方式、字段含义，以及发送和响应时机。例如收到一个 HTTP 请求后，服务端要能识别方法和路径，并按约定返回状态和内容。两个程序都能收发字节，还不足以保证它们理解彼此。

HTTP 是 Web 应用的一部分；页面格式、浏览器界面、服务端业务逻辑并不都由 HTTP 规定。本章先看 HTTP、邮件与 DNS 的具体规则，再看扩大分发规模的方法，最后把收发过程写成 Socket 程序。
