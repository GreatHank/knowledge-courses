先看一段可读的请求

GET /index.html HTTP/1.1\r\n
Host: example.test:8000\r\n
\r\n

HTTP 是超文本传输协议（Hypertext Transfer Protocol），规定客户端与服务器怎样交换请求和响应。上面显式写出了行末字符；HTTP/1.x 行末使用 \r\n。统一资源定位符（Uniform Resource Locator，URL）可以写成 http://example.test:8000/index.html：主机和端口用于选择连接目标，请求行里的 /index.html 指明所需资源，Host 首部（header）标识目标主机。这里是教学用名字，没有访问外网。

部分例子作用
方法GET请求取得目标资源的表示。
请求目标/index.html标明服务器要处理的目标。
版本HTTP/1.1声明采用的 HTTP 消息版本。
首部结束CRLF CRLF空行结束首部区，后面才可能是正文。

原书中的响应，该从哪里开始数正文

先看响应行 HTTP/1.0 200 OK，再看 Content-Type 和 Content-Length。首部之后的空行把解释方式切换到正文（body）；图中的 42092 是教材那次响应的正文长度，不包含状态行、首部和空行。终端提示信息也不属于 HTTP 报文。

Content-Type

说明正文采用什么媒体类型，例如 text/html、image/png。HTTP 不只传 HTML。

Content-Length

以字节计量正文长度；不能把汉字数量或 JavaScript 字符串长度直接填进去。

状态码

200 表示成功，404 表示未找到目标；错误响应也可以有首部和正文。

原图是历史上的明文 HTTP 演示。不能把同一套 telnet 输入直接当作 HTTPS 会话；HTTPS 还需要传输层安全（Transport Layer Security，TLS）协议过程。

一次 read 没有读完首部，很正常

下面的演示限定为：GET 的 200 响应，已给出一个合法 Content-Length，没有 Transfer-Encoding，也没有无正文的特殊情况。它按累计收到的字节寻找第一个 CRLF CRLF，再累计正文；这不是完整 HTTP 解析器。

每一步代表应用得到一段读取结果，不代表一个 TCP 包。即使首部和正文在一次读取中一起到达，也要按协议边界拆开。UTF-8 例子中，“你好”是 E4 BD A0 E5 A5 BD，正文长度为 6。
三种结束信号，不要混为一谈
观察到什么能判断什么还不能判断什么
首部空行首部结束。正文也已结束。
已读够 Content-Length本演示条件下，这条响应的正文完整。TCP 连接必须关闭。
read 返回 0对端正常结束这个接收方向上的字节流。声明的正文一定收齐；若少于长度，就是不完整响应。
HTTP/1.1 通常可以复用连接，还存在分块传输编码（chunked transfer coding）等消息定界规则。这里用最容易看清的固定长度情形入门；完整规则见 RFC 9112 §6，不能把“读到 EOF”推广为所有 HTTP 响应的结束判断。
静态和动态，区别在服务器怎样取得内容
请求的内容服务器的处理正文的可能形式
静态内容读取已有文件。HTML、图片、文本等。
动态内容运行程序，根据输入或当前状态生成内容。也可以是相同的 HTML 或图片格式。
URL 不必一一对应磁盘文件，根路径也不必由 HTTP 规定为某个固定文件。后面介绍的 Tiny 会把它映射到 home.html，这是 Tiny 的实现选择。
教材以 HTTP/1.0 和 HTTP/1.1 的文本消息解释机制。今天不能再称 HTTP/1.1 为“最新版本”：HTTP/2 使用自己的帧格式，HTTP/3 基于 QUIC；不要把本课逐行读取的方法直接套到它们的线上编码。
