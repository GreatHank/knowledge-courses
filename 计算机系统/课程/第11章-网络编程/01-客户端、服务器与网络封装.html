浏览器发出请求，谁在另一端工作

输入一个网址后，浏览器进程发送请求（request）；服务器进程读取请求，取得文件或计算结果，再发回响应（response）。先看原图左侧 Client process 到右侧 Server process 的箭头：通信双方是进程，同一台机器也可以同时运行客户端和服务器。

这里的 transaction 指一次请求与响应交互，不带数据库事务的原子性承诺。客户端、服务器描述本次交互中的角色，不能据此把一台机器永久归为某一类。

客户端

在这次交互中主动请求服务。

服务器

等待请求，访问资源并生成响应。

本章范围

围绕传输控制协议（Transmission Control Protocol，TCP）的客户端与服务器程序展开；这不是所有网络应用的唯一组织形式。

先找出程序与硬件之间的接口

看左列从 Client 到 TCP/IP 的连线：用户程序通过套接字接口（sockets interface）进入内核。再往下，内核与网络适配器配合传送数据；对端按相反方向把数据交给服务器进程。第 10 章的 read、write 仍然有用，不过访问对象换成了连接。

程序通常不逐个操纵网线上的帧，也不直接指定每个路由器。套接字把这些工作隔在接口之下，但传送延迟、错误和短计数仍会出现在程序可见的行为里。

跨过一个路由器，哪一层发生变化

沿图观察新增或移除什么解决什么问题
主机 A：步骤 1 → 3应用数据外加互联网包首部 PH，再加局域网帧首部 FH1。PH 服务于跨网络传送；FH1 服务于当前 LAN。
路由器：步骤 4 → 5去掉 LAN1 的封装，按目的 IP 转发，再套上 LAN2 的 FH2。两段网络可以使用不同的帧格式。
主机 B：步骤 6 → 8逐层去掉封装，将数据交给上层。服务器得到应用数据，不必自己拆局域网帧。

IP 是网际协议（Internet Protocol）。在这个没有 NAT 的简化例子中，目的 IP 地址指向主机 B；第一段局域网的帧则交给下一跳路由器。不能把“去 B”与“当前这一步交给谁”混成一个地址。图把细节压缩成 PH 和 FH，没有单独画 TCP 首部；路由器也可能修改 IP 首部中的 TTL 等字段，不能理解成整个 IP 包逐位不变。

不同层承诺不同的事

机制教材中的用途不应由此推出
集线器／网桥教材用它们说明局域网连接与分段转发。书中的设备示意就是今天每个网络的部署方式。
IP按地址跨越互联网络，提供尽力而为的传送。每个 IP 包都必定到达且有序。
TCP向应用提供有序、可靠的字节流；失败仍可能以错误或超时结束。一次 write 就是一条完整应用消息，或对方已经处理完。

原书 PDF 961 把 UDP 展开成了 “Unreliable Datagram Protocol”；正式名称是 User Datagram Protocol。这不影响教材用它对照 TCP 的讨论，但名称应按 RFC 768 纠正。

回到总图：先知道数据要送给谁

“请求怎样跨越网络”连到“地址、端口与名字”：程序还要把人输入的名字变成接口可用的地址，并指定目标服务。下一课从一个 IPv4 地址的四个字节开始。
