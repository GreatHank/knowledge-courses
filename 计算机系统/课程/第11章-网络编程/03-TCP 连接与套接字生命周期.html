TCP 用本地 IP、本地端口、远端 IP、远端端口组成的四元组（four-tuple）区分连接。端口是协议里的 16 位编号，不是进程 PID，也不是物理插孔。不同连接可以共享服务器端口，因为另一端不同。

看原图：保留 listenfd，再增加 connfd

先看最下方 Server：listenfd(3) 还在，connfd(4) 是 accept 新返回的描述符（file descriptor）。以后向这个客户端读写，使用 connfd；接待下一次连接，仍把 listenfd 传给 accept。编号 3、4 只表示教材这一次的分配结果。

调用对这个套接字做什么成功不意味着
socket创建套接字并取得描述符。已经连到远端。
bind指定本地地址和端口。已经开始等待连接。
listen把套接字设为被动监听状态。应用正在读取某个客户端的正文。
connect主动发起到远端的连接。远端应用已经 accept 或处理请求。
accept从监听入口取得连接，返回新的描述符。原监听描述符被替换或消失。

把内核建连和应用接待分开

单独打开交互图 · Archify 伴读示意。时序自上而下；虚线返回与实线请求分别标出。

重点看“握手（handshake）完成，connect 可返回”到“accept”之间的间隔：服务器内核可以先完成 TCP 建连，把连接放入队列。服务器程序稍后调用 accept，再取出连接。另一种合法顺序是 accept 先调用并阻塞等待；原书图 11.14 展示的是这一种。

Linux 的 listen backlog 用来限制等待 accept 的已完成连接队列，不能直接解释成服务器总共最多服务多少个客户端；尚未完成握手的队列另有控制。依据 listen(2)、connect(2) 与 accept(2)。

动手观察描述符是否还在

这是离散步骤模型，只追踪本例的描述符、队列和客户端状态。它省略报文重传、超时和内核调度；点击一步不代表固定耗时，也没有实际运行 socket 调用。
accept 的地址参数装的是谁
struct sockaddr_storage peer;
socklen_t peerlen = sizeof peer;
int connfd = accept(listenfd, (struct sockaddr *)&peer, &peerlen);
if (connfd < 0) {
    perror("accept");
    /* 调用者决定重试、结束或其他处理。 */
}
peer 装的是对端地址。调用前，peerlen 告诉内核缓冲区有多大；返回后，它报告地址的实际长度。每次新的 accept 都应重新设置这份长度。sockaddr_storage 为不同地址族预留足够空间。
原书 PDF 973 的原型写作 int *addrlen；当前 Linux 接口是 socklen_t *，教材后面的服务器程序也采用 socklen_t。这里按实际接口给出片段。
连接建立后，仍然按返回值读写
一次 write 的字节可能被对端分几次 read 读到；多次 write 也可能被一次 read 合并取出。TCP 不保留应用的写调用边界。对端正常结束发送方向后，接收方先读完剩余字节，随后 read 才返回 0；连接复位等情况可能返回错误。
本课讨论阻塞接口。非阻塞 connect 可能以 EINPROGRESS 表示正在进行，不能照搬这里的“调用返回即建连成功”。回到总图，下一课准备 socket、connect 和 bind 真正需要的地址参数。
