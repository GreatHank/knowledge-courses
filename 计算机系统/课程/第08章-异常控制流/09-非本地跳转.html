bar 出错，能直接回到 main 的恢复点吗

正常调用沿 main → foo → bar 前进，返回也逐层经过各自的调用点。若 bar 发现错误，逐层传递错误码是一种处理方法；教材这里展示另一种控制转移：直接恢复到 main 先前保存的位置。

非本地跳转（nonlocal jump）跳过正常的逐层返回。setjmp 保存供以后恢复的执行环境（execution environment）；longjmp 使用这份环境，让先前的 setjmp 表现为再次返回。

同一个 setjmp 位置，两种返回来源

单独打开交互图 · Archify 机制示意。

static jmp_buf env;

static void bar(void) {
    longjmp(env, 2);
}
static void foo(void) {
    bar();
}
int main(void) {
    switch (setjmp(env)) {
    case 0:
        foo();
        break;
    case 2:
        puts("recovered from bar");
        break;
    }
    return 0;
}

伴读 C 示例需要 <setjmp.h> 与 <stdio.h>。初次直接执行 setjmp 得到 0，因此调用 foo。图中最后一条 bar→main 的线跳过 foo 的正常返回，让同一 setjmp 得到 2，进入 case 2。

longjmp 本身不返回。若第二个参数传 0，setjmp 仍会得到 1，以便与初次返回的 0 区分；这里的 2 是程序选择的分支值，不是内核错误码。

保存的环境，不是整个程序的时间快照

对象或条件longjmp 后需要怎样看
已结束函数的栈帧不能跳回；保存环境的函数必须仍在活动
被跳过的清理代码不会自动执行，打开文件或已分配对象不会因此自动释放
堆与全局对象的修改不会自动回滚
setjmp 所在函数中被改过的非 volatile 自动局部变量满足相应条件时值不确定，不能依赖原值或新值
另一个线程保存的环境不能用来跨线程跳转

局部变量这一条限定为：在 setjmp 和 longjmp 之间改变、属于调用 setjmp 的函数、且未声明 volatile 的自动变量（automatic variable）。不要把它扩大成“所有变量都丢失”，也不要把 volatile 当成资源恢复工具。条件见 setjmp/longjmp(3)。

图中的跨层箭头表示恢复控制位置与必要的机器状态，绝不表示逐个执行各层 return 或清理语句。与 C++ 异常比较时还要考虑语言提供的栈展开与析构规则，不能直接等同。

从信号处理函数跳出，还要考虑屏蔽状态

sigsetjmp(env, 1) 请求同时保存当前信号屏蔽集合，之后 siglongjmp 恢复它。先保存有效环境，再允许相应处理函数跳入，是这个例子的前提。

教材 PDF 822 页 的文字把 pending 与 blocked 都写进保存恢复说明。接口实际保证的是按条件保存、恢复信号屏蔽集合，不能据此认为已发生的待处理信号被回滚；参见 sigsetjmp/siglongjmp 说明。

若处理函数打断了一个不安全函数，随后跳出它，内部状态可能仍停在修改到一半的位置。能恢复控制，不代表可以安全继续调用任意库函数；原图用于解释机制，不应直接当成通用“出错就重启”模板。

回到章节图：这是“同一流内跳转”的支路，没有创建进程，也不是内核在两个进程间切换。下一课用这些区别解释实际运行现象。
