孩子太快结束，反而暴露了问题

shell 的主流程想按 fork → addjob 执行，处理函数收到 SIGCHLD 后却会做 waitpid → deletejob。如果孩子先退出，处理函数可能在 addjob 前运行：它删不到记录，主流程随后却添加了一条已经结束的作业。

这是竞态条件（race condition）：结果依赖不受程序控制的事件交错。两个函数各自的语句顺序没错，合在一起却缺少必要的先后约束。

步发生了什么

保护区间必须从 fork 之前开始

执行位置主流程／子流程的动作为什么放在这里
fork 前父进程屏蔽 SIGCHLD，保存旧 mask孩子尚未存在，来得及关闭处理函数插入的窗口
创建时调用 fork，检查创建结果失败时没有孩子可登记，错误路径也要处理 mask
fork 后·子分支子分支恢复旧 mask，再 exec避免把 shell 暂时的屏蔽传进新程序
fork 后·父分支父分支 addjob此时孩子可退出，但 SIGCHLD 的处理被延后
登记后·父分支父分支恢复旧 mask处理函数此后才能看到已经登记的作业

fork 后父子分支可以交错，子分支恢复 mask 与父分支 addjob 之间没有规定先后。屏蔽没有阻止孩子执行或终止，只延后本线程的信号递送（signal delivery）。把屏蔽放到 fork 后面仍然太晚：孩子和处理函数可能先跑完。

教材还在访问作业表时屏蔽更完整的信号集合，保护共享表操作。它与“先登记、再允许回收”的时序要求各有作用。本课限单线程 shell，不能把信号屏蔽直接推广为线程之间的互斥锁。

检查一次，再 pause，为什么仍会等不到

/* 错误的等待结构 */
while (!child_done)
    pause();

在演示里选“检查后 pause”。主流程读到 child_done=0，准备等待；就在调用 pause 前，孩子退出，处理函数把它改为 1 并返回。接下来的 pause 不会因“刚才处理过信号”自动返回。如果再没有其他信号，程序就继续睡下去。

把 pause 改成 sleep 只能改变症状：轮询（polling）可能晚一些发现状态，还要选择等待间隔。这里需要把“允许通知到达”和“开始等待”作为不可分开的操作。

sigsuspend 关闭检查与睡眠之间的空隙

单独打开交互图 · Archify 机制示意。

沿图中 sigsuspend(prev) 的连线看：内核临时替换屏蔽集合并等待信号，这两个动作作为一个原子等待（atomic wait）操作完成。已经 pending 的 SIGCHLD 因而可以触发处理函数，不会掉进“通知已处理，但尚未睡眠”的空隙。

处理函数返回后，sigsuspend 恢复调用前的屏蔽集合，并以 -1／EINTR 返回。主流程仍在屏蔽 SIGCHLD 的状态下重新检查条件；其他信号也可能唤醒它，所以要用 while，而不是假定“醒来就意味着孩子结束”。

/* 前提：单线程、只有一个目标孩子；SIGCHLD 原本未屏蔽。
   已检查安装的处理函数：回收该孩子后将 child_done 置 1。
   其他处理函数不改 child_done；fork 前已经屏蔽 SIGCHLD。
   prev 保存屏蔽前的 mask；父进程在这里等待。 */
while (!child_done) {
    if (sigsuspend(&prev) < 0 && errno != EINTR) {
        perror("sigsuspend");
        exit(EXIT_FAILURE);
    }
}
if (sigprocmask(SIG_SETMASK, &prev, NULL) < 0) {
    perror("sigprocmask");
    exit(EXIT_FAILURE);
}

这是等待部分的伴读片段，child_done 需声明为 volatile sig_atomic_t；不是可脱离安装、创建和回收步骤单独运行的完整程序。教材 PDF 818 页 用三行伪代码解释 sigsuspend 时写了 SIG_BLOCK，但正文描述的是“替换”屏蔽集合，接口语义对应 SETMASK。三次独立调用仍不具备原子性，不能据伪代码自己拼装替代；核对 sigsuspend(2)。

回到两条不同的正确性条件

登记与回收的先后

在创建孩子前屏蔽，登记后恢复，保证处理函数不会抢在 addjob 前处理退出。

检查与等待的衔接

屏蔽时检查条件，用 sigsuspend 原子地解除屏蔽并等待，醒来再检查。

两者都用到屏蔽，但解决的空隙不同。下一课离开进程间通知，回到同一执行流内部：深层调用怎样跳回外层保存的位置。
