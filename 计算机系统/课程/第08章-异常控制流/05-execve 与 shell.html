子进程已存在，为什么还要 execve

输入 /bin/ls -l 后，fork 得到的子进程仍在执行 shell 的程序。它要运行 ls，需用 execve 装入新的程序映像（program image）。

fork

创建一个新的进程；父子开始时执行同一份程序代码，返回值不同。

execve

替换当前进程的程序映像；成功后 PID 不变，旧调用位置不会再返回。

新程序从自己的入口开始，通常由启动代码调用 main。不要把 execve 成功画成“返回到 shell 子进程中的下一行”。

参数是一组指针，末尾还要有空指针

char *argv[] = { "/bin/ls", "-l", NULL };
char *envp[] = { "LANG=C", NULL };
execve(argv[0], argv, envp);
perror("execve");  /* 能走到这里，就说明失败 */
_exit(127);

这是单线程 shell 的子进程分支片段。argv 的最后一个元素是空指针，各个字符串内部还各有自己的 NUL 结束字节；两种终止标记不能互换。argv[0] 按惯例表示程序名，环境数组（environment array）则由形如 NAME=value 的字符串组成。

execve 使用给定路径，不替你按 PATH 搜索。示例只提供 LANG=C，因此新程序收到的环境也只有这一项；实际 shell 通常传入适当的继承环境。这里失败后用 _exit(127) 结束子分支，避免继续误走父进程的交互流程。

先看“内核 → shell”的正 PID 返回，再看“内核 → 子进程”的 0 返回：它们区分两条路径。父进程可以先进入 waitpid；子进程随后 execve 并运行新程序。图给出一种合法交错，不承诺父子谁先获得 CPU。

图最下面的 waitpid 返回与回收相连：子进程已经终止并留下状态，父进程才能取得它。execve 失败则应由子分支报告并终止，父进程仍需回收。

替换程序时，哪些状态仍会留下

内容execve 成功后的情况
程序的代码、数据和栈被新程序映像替换
进程 PID保留
文件描述符通常保留；设置 close-on-exec 的描述符关闭
捕获信号的处理函数恢复为默认处置；旧代码地址已不能继续当处理函数
信号屏蔽集合保留；子进程需要在 exec 前恢复不应继承的屏蔽

这几项正好解释 shell 怎样先安排输入输出，再执行命令，也解释为什么不能把父进程暂时屏蔽的 SIGCHLD 无意传给新程序。具体规则见 execve(2) 与 signal(7)。

教材的小 shell 做到了什么，还缺什么

顺着原图看：解析命令后先判断内建命令；普通程序走 fork／execve；前台分支等待孩子，后台分支直接返回提示符。像 cd 这样要改变 shell 自身状态的命令，需要在相应的 shell 上下文中执行。

这个简化版本没有完成后台子进程的回收，也没有完整作业控制。用户没有再输入命令时，后台孩子照样可能退出；shell 因而需要一种异步通知。章节图“进程控制 → 信号通知”的连线就从这个缺口引出。
