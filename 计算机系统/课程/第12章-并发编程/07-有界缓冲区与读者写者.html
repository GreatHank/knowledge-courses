队列有空位，与现在谁能修改队列，是两个问题

生产者（producer）要放入一项任务，消费者（consumer）要取出一项任务。队列空时，消费者不能取；队列满时，生产者不能放。即使容量允许，同时修改队头、队尾和数组也需要互斥。

slots = n

可供生产者预订的空位，空队列初始有 n 个。

items = 0

可供消费者预订的已发布项目，空队列初始为 0。

mutex = 1

保护队列内部修改，同一时刻只有一个持有者。

设 n > 0。slots 和 items 管“现在是否有资源”，mutex 管“谁正在修改结构”。这三个信号量不能随意合成一把锁。这样的有限容量队列称为有界缓冲区（bounded buffer）。

先预订资源，再修改，再发布

插入任务取出任务
P(slots)：预订一个空位。P(items)：预订一个已有项目。
P(mutex)：取得队列修改许可。P(mutex)：取得队列修改许可。
更新 rear，写入任务。更新 front，取出任务。
V(mutex)：结束结构修改。V(mutex)：结束结构修改。
V(items)：发布一个可取项目。V(slots)：归还一个空位。

原图用 (++rear) % n 与 (++front) % n 绕回数组；front、rear 初始都是 0，因此第一次使用槽位 1 % n。取模后的两个槽位索引相等，可能对应空队列，也可能对应满队列；front、rear 本身在原例中仍不断递增。判满判空应依据 items / slots 和同步协议，不能只比较取模结果。索引使用 int，长期使用还应处理其溢出；销毁前必须确认没有使用者和等待者，并安排同步对象的清理。

中间状态里，许可已经预订但项目还没发布

容量 2；观察每个 P/V 前后许可数和实际队列。

教学状态演示，不创建真实线程，也不模拟 C 未定义行为或硬件内存模型。
从空队列开始，生产者完成 P(slots) 后，slots 从 2 变成 1，但 items 仍是 0。那一个位置已被生产者预订，尚未成为消费者可取的项目。只有没有操作进行到一半的稳定状态，才可直接用 slots + items = n；不能把它当成每个瞬间都成立。
演示把 mutex 内的队列修改合成一个原子步骤，突出许可的预订和发布；锁竞争本身由前一课解释。
把等待空位放进锁内，会堵死谁
错误顺序：先 P(mutex)，再 P(slots)后果
队列已满，生产者先取得 mutex。随后等待空位，手里却不放开 mutex。
消费者准备取出一项。需要 mutex，因而也等待。
谁能产生空位？只能是消费者；它现在无法进入，双方互相卡住。
教材把 P(slots) / P(items) 放在 P(mutex) 前，是为了避免持有队列锁时等待队列资源。第 12 课会把这种等待关系画成环。
多个读者可以一起读，写者需要独占
沿 reader 的上半段看：mutex 保护 readcnt；第一个读者取得 w，后续读者只增加计数。读操作在释放 mutex 后进行，所以读者可以重叠。最后一个读者退出时归还 w。writer 则直接用 P(w) / V(w) 包住写操作。
状态谁能进入
已有读者，readcnt > 0新的读者可能加入；写者等待 w。
最后一个读者退出readcnt 变为 0，V(w) 让写者有机会取得独占许可。
写者持有 w新的第一位读者在 P(w) 等待，其他写者也等待。
取得 w 和归还 w 的可能不是同一个读者，所以这里的 w 不能直接换成要求持有者解锁的 pthread mutex。这个方案偏向读者；不断加入的读者可能让写者长期等待，信号量本身也不提供本课所需的 FIFO 保证。正确的互斥不等于公平。
回到同步节点：我们已经能协调“谁能改”以及“什么时候有资源”。下一课把任务换成 connfd，把消费者换成工作线程。
