把 0 到 n−1 分成互不重叠的区间

教材让 t 个线程各处理 n/t 项，先假定 n 能被 t 整除。线程 i 负责半开区间 [i·n/t, (i+1)·n/t)。区间既不重叠，也不遗漏；每个线程的参数对象独立，主线程等所有线程结束后再验算。

/* 伴读小例：n = 12，t = 3 */
线程 0：0, 1, 2, 3     部分和 6
线程 1：4, 5, 6, 7     部分和 22
线程 2：8, 9, 10, 11   部分和 38
join 全部线程后：6 + 22 + 38 = 66

这项求和本可直接用 n(n−1)/2 计算。教材保留循环来比较并行方案，并用公式校验结果。实际 C 计算还需保证中间乘法和总和不溢出。

正确地加锁，却把细小工作变成了争抢

每次只做一个加法，却都要 P 和 V，还要争用同一个 gsum。即使各线程负责不同的 i，它们仍在更新同一结果，所以大量时间花在同步，而可重叠的有效计算很少。

教材四核机器、n = 2³¹ 的实验中，一线程用 68 秒，四线程用 719 秒。这是该书的测量结果，不是本机运行结果，也不能直接预测另一台机器。原始数据在 PDF 1051、1054。

各算各的，再合并结果

线程 i 只修改 psum[i]，其他工作线程不访问这一元素；主线程等 join 全部完成后才合计。数组仍是全局对象，但不同元素被分给不同线程独占写入，因此这里不需要每次加法都争抢一把锁。

再进一步，先在局部 sum 中累加，结束时只把结果写入 psum[i] 一次。这个改动把第 5 章“减少循环里的内存访问”用到了并行程序中。编译器最终如何生成指令仍需结合实际代码和编译选项检查。

沿横轴看，线程数从 4 增到 8、16 时，核心数没有继续增加。此例没有得到更多执行资源，还增加了调度等开销。对于会等待 I/O 的任务，合适的线程数可能不同，不能把这个求和结论当成所有服务器的线程数公式。

核心数 p 与线程数 t 不能混作同一个分母

Sₚ = T₁ / Tₚ；Eₚ = Sₚ / p。 这里 Sₚ 是加速比（speedup），Eₚ 是并行效率（parallel efficiency）。四核四线程这一列，1.06 / 0.28 ≈ 3.79，效率约 94.6%。八线程那列仍只有四个核心，所以效率分母仍是 4。

测量口径保持什么不变能回答什么
强扩展 strong scaling问题规模固定。增加核心后，同一份工作能快多少？
弱扩展 weak scaling每个核心承担的工作量大致固定，总规模随核心数增加。机器变大时，能否按比例完成更多工作？
绝对加速比（absolute speedup）基线用合适的顺序版本。并行方案相对顺序方案有多少收益？
相对加速比（relative speedup）基线用并行程序自身在一个核心上的时间。这个并行版本扩展得怎样？基线自身的额外开销可能抬高比例。

效率不是 CPU 利用率的另一种写法；它是基于所选基线和运行时间的比例。也不要把教材常见的 0–100% 范围理解为定义强制的数学上界。
