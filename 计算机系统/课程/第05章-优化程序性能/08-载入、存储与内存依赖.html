数组与链表：下一次地址从哪里来

连续数组

value = data[i];
i++;

知道基址和下标，就能计算后续元素地址。若资源足够，可以提前发起多个读取。

沿链表走

while (ls) {
    len++;
    ls = ls->next;
}

下一结点地址存放在当前结点里；这次读取完成前，后续地址通常还不知道。

依赖步骤数组顺序访问链表遍历
先确定地址基址 + 下标 × 元素大小当前 ls
执行载入读当前元素读 ls->next
准备后续载入通常不依赖当前元素值必须使用刚读到的指针

链表（linked list）遍历形成载入结果 → 下一次载入地址的真实依赖。教材在数据命中缓存的实验中测得约 4.00 周期/结点，与参考机 L1 载入延迟一致。两套载入单元也无法让一条这样的链同时取得尚未知地址的后继结点。

数组也不是一概没有读取依赖，例如 i = data[i] 同样可能构成地址追逐。要看值如何产生下一次地址，不能只看容器的名字。这里讨论的是缓存内访问；缓存未命中及局部性留到第 6 章。

写入不必每次都等缓存更新完成

沿原图右侧看，Store buffer 记录尚未完成的写入地址和数据。随后看中间两条相反方向的箭头：载入先拿地址检查待写记录，必要时直接取出对应数据。这叫存储到载入的转发（store-to-load forwarding）。

本课沿用教材简化模型，重点是同一地址、相同访问宽度的情形。现实硬件对部分重叠、对齐和转发有额外限制，不能仅凭图就断言任何重叠都能立即转发。图中的 store buffer 属于处理器微体系结构，与 C 标准 I/O 的用户态缓冲区不是同一层。

同一段代码，只换地址，依赖就不同

/* 根据教材 write_read；本例 n=3，不发生整数溢出 */
long val = 0;
for (long cnt = n; cnt > 0; cnt--) {
    *dst = val;
    val = *src + 1;
}

两次独立实验都从 a = [-10, 17] 开始。src 都指向 a[0]；只改变 dst。

轮次dst 指向 a[1]：数组；下一轮 valdst 也指向 a[0]：数组；下一轮 val
初始[-10, 17]；0[-10, 17]；0
1[-10, 0]；-9[0, 17]；1
2[-10, -9]；-9[1, 17]；2
3[-10, -9]；-9[2, 17]；3

看右列：先写入的 val 马上成为 *src 的输入，形成“写数据 → 读回数据 → 加 1 → 下一轮写数据”的跨轮依赖。左列的读取始终得到 -10，不需要等待另一地址上的写入数据。

教材原版长循环的 CPE 分别约为 1.3 与 7.3。右列增加的等待来自写后读依赖（read-after-write dependency），并不是因为它一定访问了更远的内存。这里的代码采用 for 形式便于看清轮次，不把教材计时归为这段改写的本机实测。

两个层次的别名，放在一起看

层次不知道什么需要怎样处理
编译器优化，见第 1、3 课不同指针运行时会不会重叠？保留所有合法输入需要的语义，或依靠可证明的接口条件
处理器执行，本课尚未算出的载入／存储地址是否冲突？确定依赖，必要时等待或转发，保持正确的读写关系

两个层次面对相似的地址关系，任务却不同。编译器决定能生成怎样的代码；硬件在执行这份代码时，继续处理动态地址产生的依赖。缓存命中只能缩短获取数据的时间，不能让真正的数据依赖消失。
