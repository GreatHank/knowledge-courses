§1.1 · hello.c 在计算机里是什么？

先看图的左上角。教材的程序如下；这次只需知道它会输出 hello, world 并换行，随后结束，不必先逐行拆解 C 语法。

#include <stdio.h>

int main()
{
    printf("hello, world\n");
    return 0;
}

在编辑器里，你看到的是字符。保存为 hello.c 后，文件内容是一串字节。教材这个纯 ASCII 示例中，每个字符对应一个字节：

编辑器显示的字符对应字节的位模式按无符号数解释
#0010001135
i01101001105

一个位（bit）的值是 0 或 1；本书的一个字节（byte）由 8 位组成。ASCII 是字符与编码值之间的一套对应规则。这里的“一字符一字节”只针对这个示例，不能直接套到中文。

再只看第一行：同样的 00100011，按 ASCII 解释得到字符 #，按无符号整数解释得到数值 35。位没有改变，解释方式改变了。

Information Is Bits + Context
信息是位，加上解释这些位的上下文。

回到章节图：左上角的 hello.c 用位来编码 C 文本。它与右侧可执行程序都由位组成，但组织方式和用途不同。因此，“源代码已经是 0 和 1”并不意味着 CPU 可以直接照着这些字符执行 C 语句。

这就引出了顶行第一条“翻译与链接”连线：怎样从表示源代码字符的字节，得到包含机器指令的可执行程序？这是 §1.2 要解决的问题。

§1.2 · 从 hello.c 到 hello：五种文件，四个阶段

章节位置：顶行“hello.c”到“可执行文件 hello”的连线。下面把这条线展开；实线跟着文件走，紫色虚线表示构建之后的运行。

放大四阶段图

① 预处理：把 C 文本准备好

#include <stdio.h>
       ↓
头文件中的声明等内容被展开

.c → .i：处理 include、宏和条件编译。输出仍是 C 文本。

知道 printf 怎样调用，仍不等于已有 printf 的实现。此处头文件提供声明等内容；标准库另行提供函数实现。

② 编译：把 C 的操作落实为指令

printf("hello, world\n");
       ↓
call puts  /* 教材汇编中的一行 */

.i → .s：生成汇编文本。编译器可以优化，并非每个 C 语句都对应一条汇编指令。

这里的固定字符串输出可转为 puts 调用。寄存器和调用细节到第 3 章再展开；实际生成结果依编译器与选项而异。

③ 汇编：把指令文本编码

汇编中的指令助记符
       ↓
机器指令的字节编码

.s → .o：输出包含机器代码的目标文件，还带有供链接使用的符号、重定位等信息。

.s 便于人读；.o 已有机器指令。但有些跨文件引用尚未接好。

④ 链接：把各部分接成程序

hello.o + 所需目标文件与库
       ↓
可执行文件 hello

找到所需函数或变量的定义，组织代码与数据，处理地址引用。

本图采用教材简化模型。动态链接允许部分工作留到装载或运行时；不把所有库都复制进可执行文件当成普遍规则。

gcc 为什么看起来“一步就完成”？

gcc -o hello hello.c

gcc 在这里是编译驱动程序，负责组织各阶段。日常说“编译项目”往往包含整个构建；图中“编译”特指第二阶段。

停在哪一步对应命令（教材环境示意）得到什么
预处理结束gcc -E hello.c -o hello.i展开后的 C 文本
编译结束gcc -S hello.i -o hello.s汇编文本
汇编结束gcc -c hello.s -o hello.o可重定位目标文件
链接结束gcc hello.o -o hello可执行文件

以上命令用于说明阶段，本轮未运行。默认的一条 gcc 命令不保证把所有中间文件留在磁盘上。

放大最后一步：有机器指令，为什么还需要链接？

用一个补充例子看清楚：main.c 调用 add，函数体放在另一个文件中。这里只看普通的分文件构建，省略跨文件优化。

main.c · 声明并调用

int add(int, int);  // 声明

int main(void) {
    return add(2, 3);
}

编译器知道 add 接受两个 int、返回 int；函数体可以在别处。main.o 可以先记录“这里引用了 add”。

add.c · 给出定义

int add(int a, int b) {
    return a + b;
}

函数体给出了实现。构建出的 add.o 定义了 add，能为另一份目标文件提供这个符号。

放大链接局部图

看两条进入“符号解析”的线：main.o 需要 add，add.o 提供 add。链接器先让引用找到定义，再安排各部分的位置、修补相关地址引用。这两件事分别叫 symbol resolution 与 relocation。

输入结果原因
gcc -c main.c -o main.o可以得到 main.o先翻译调用方，留下外部引用
仅用 main.o 链接本示例找不到 add 的定义声明没有带来函数实现
gcc main.o add.o -o prog可生成 progadd.o 已单独编译并提供定义

这是便于理解的自拟 C 示例，未在本机执行；它返回计算结果作为退出状态，不打印数字。链接两项任务依据 §7.2（PDF 第 710 页），此处提前借用来解释 §1.2，不展开第 7 章细节。

§1.3 · 知道各阶段，就能定位问题

看到的现象先检查哪里为什么
找不到头文件预处理与头文件搜索路径待翻译的 C 文本还没准备齐
C 语法或类型使用错误编译阶段与源码无法形成合法的目标程序
undefined reference / 未定义引用链接阶段与所需目标文件、库有调用，却没有找到对应定义
能生成程序，但跑得慢或运行出错运行行为与对应系统机制构建成功不能证明逻辑正确，也不能保证高性能

教材 §1.3 将价值归为优化性能、理解链接错误与避免安全漏洞；上表是把这些动机落实到常见现象的补充整理。
