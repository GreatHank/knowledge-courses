共享库从哪里进入程序

gcc -shared -fpic -o libvector.so addvec.c multvec.c
gcc -o prog2l main2.c ./libvector.so

看图中两条来自 libvector.so 的箭头：构建阶段提供符号与重定位相关信息；运行时才映射需要的代码和数据。这里没有把这个库的整段代码嵌进 prog2l。生成可执行文件时仍做了一部分静态链接工作，之后还保留动态处理的任务。

这里的命令沿用教材的本地共享库（shared library）例子。库的构建路径、程序记录的依赖名和运行时的搜索路径不能混为一谈；“链接时找得到”并不能证明“换一个运行目录后也找得到”。-L 影响构建时查库，不等于设置运行时搜索目录。

共享的是代码页，不是所有变量的值

文件层面

多个程序可以依赖同一个共享库文件，不必各自嵌入一份库代码；系统也可能同时安装多个版本。

进程层面

同一库的可共享代码页可供多个进程映射。普通可写变量的修改影响当前进程中的副本，不会把计数值自动同步给其他进程。

若每个进程都要把各自的绝对地址改写进代码页，代码共享就会受影响。下一课用 PIC 解释怎样把可变地址留在数据结构中。

更新库也有条件：新库需要保持应用所依赖的应用二进制接口（application binary interface，ABI），包括调用约定和数据布局等。动态链接（dynamic linking）使替换库成为可能，却不会自动修复参数布局、符号版本或行为的不兼容。

程序运行起来以后，也可以主动加载

操作得到什么关键边界
dlopen(path, flags)一个库句柄句柄不是 addvec 的函数地址
dlsym(handle, "addvec")符号对应地址调用者仍须使用正确的函数类型
函数指针调用执行库函数地址查询不是跨进程调用
dlclose(handle)释放这一份库引用是否真的卸载受引用及加载状态影响，不能继续使用失效指针

沿代码 16 → 23 → 30 行看：先打开库，再找函数，最后执行。与上一张图的区别是请求来自已经运行的应用。教材把这用于可选功能与服务器模块；它解释的是机制，并不表示所有服务器都采用这一架构。

失败检查与绑定时机

/* 补充：对已有有效 handle 查询符号时的错误检查 */
dlerror();                    /* 清掉旧错误 */
void *addr = dlsym(handle, "addvec");
const char *error = dlerror();
if (error != NULL) {
    fprintf(stderr, "%s\n", error);
    /* 当前调用路径应停止，不能使用 addr */
}

dlsym 返回 NULL 不能单独作为所有情况的失败判据，应按上面顺序检查 dlerror。这是依据 Linux dlsym 手册补充的片段。教材中的函数指针（function pointer）赋值属于本章 Linux／POSIX 背景，不能当作任意平台 ISO C 的通用承诺。

RTLD_NOW 要求在 dlopen 返回前完成相应未定义符号解析；RTLD_LAZY 允许函数引用延后绑定，变量引用仍需及时处理。dlclose 成功也不保证库立刻从地址空间移除。具体条件见 Linux dlopen 手册。

回到章节图：装入时和运行中都可能出现动态链接。它们共享“找定义、绑定地址”的工作，但触发者和时机不同。
