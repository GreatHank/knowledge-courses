把输入逐字节复制到输出

沿第 7 行 Read → 第 8 行 Write 看：读到一个字节才写一个字节，返回 0 时结束。图中的大写 Read、Write 是教材 csapp.h 配套的错误处理包装函数；标准 Unix 接口写作 read、write。直接换成小写却不处理 -1，会改变程序的错误行为。

这段程序每复制一个字节就调用一次 Read 和一次 Write。扩大每次请求的字节数可以减少调用次数，但也需要处理返回量不足的情况。

返回值是已完成的字节数

ssize_t nr = read(fd, buf, capacity);
/* nr > 0：只处理 buf[0 .. nr-1]
   nr == 0：在 capacity > 0 的普通文件／字节流读中，表示 EOF
   nr == -1：读取失败，查看 errno */
一次请求可能返回应用随后知道什么
read：想要 100 B20已有 20 B 可用，不能假定另 80 B 已填入。
read：想要 100 B0本次到达输入末尾，即 EOF（end-of-file）；普通文件后来增长等变化另论。
read：请求 0 B0不能据此断定 EOF。
write：想写 100 B20前 20 B 已写入，下一次应从第 21 B 续写。
read / write-1错误；先辨别原因，不能把它当字节数。

请求长度使用无符号 size_t，返回值使用有符号 ssize_t，才能同时表达字节数与 -1。read 不会自动补 C 字符串终止符；即使得到 20 个字节，也不能不加处理就用 %s 打印。

一次短读成功之后，位置怎样变化

动作读到的数据普通文件偏移
初始文件 abcdef；偏移 0尚未读取0
请求 4 B，本次返回 2ab2
再请求剩余 2 B，返回 2cd4

这里人为设定第一次只返回 2，用来说明短计数（short count）。偏移增加实际读取量；第二次应把数据放在 buf+2，而不是覆盖 buf 开头。是否要凑够 4 B，由应用协议决定：按块读满、按行结束、读到当前可用数据，是三种不同要求。

短计数不是网络专有现象

教材列出文件末尾、终端和网络等常见原因。PDF 933 把磁盘读写“不会短计数”说得过于绝对：例如磁盘空间不足，write 可能只写入一部分后返回正数。程序应在所有这些接口上检查实际返回量。见 Linux read(2) 与 Linux write(2)。

EINTR

调用在尚未传送数据时被信号打断，可能返回 -1/EINTR。已经传送部分数据时，也可能直接返回正的短计数。

EAGAIN

非阻塞描述符暂时不能继续。它不是 EOF，也不适合用无等待的无限重试循环处理。

TCP 字节流

一次 write 与一次 read 不形成固定配对；一条应用消息可能由多次 read 拼成。

write 成功只说明相应字节被接口接受，不能单独证明断电后仍能找回。缓冲（buffering）与持久化的区别会在第 8 课接上。

把“要多少”与“得到多少”分开

回到“字节读写与返回值 → 可靠循环”：应用如果确实要读满 n 字节，就要保存已完成量、剩余量与目标指针。下一课把这个循环完整展开。
