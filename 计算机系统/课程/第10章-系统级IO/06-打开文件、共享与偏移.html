同一个 foobar，先读到 f 还是 o

/* 以下用教材错误处理包装；每次 Read 都请求 1 B。 */
int a = Open("foobar.txt", O_RDONLY, 0);
int b = Open("foobar.txt", O_RDONLY, 0);
Read(a, &c1, 1);
Read(b, &c2, 1);

假设文件内容为 foobar，且两次读取都成功，这里 c1 和 c2 都是 f。第二次 open 建立了独立的打开文件描述（open file description），所以它没有接着第一次读到 o。变量 c1、c2 为 char；示例省略后续关闭。

单独打开交互图 · Archify 伴读示意；关键关系均显示在图中。

看左侧 fd 3 和 fd 4 的线：它们先到不同的 X、Y，再汇合到同一文件对象。共享文件内容，不必共享文件偏移（file offset）。上方子进程的线直接汇入 X，才会共享 k₁。

教材把内核状态分成三层

层次谁持有这课要观察的字段
描述符表每个进程各一份小整数 fd 对应哪一个打开文件描述。
打开文件表可被多个描述符引用当前文件偏移、打开状态标志、引用计数。
v-node／文件对象表示底层文件文件类型、大小和其他元数据。

这是教材帮助理解共享关系的抽象，不是要求逐字段照搬某版 Linux 的结构体。描述符标志如 FD_CLOEXEC 属于各描述符；文件偏移和文件状态标志属于打开文件描述。见 Linux open(2) 与 Linux dup(2)。

fork 复制了表，为什么位置仍共享

看父表与子表指向 File A 的两条线：两份表中的引用（reference）汇合到同一个对象。若子进程先读 f，父进程等待子进程完成后再读，就会读到 o；去掉等待，谁先取得哪个字符取决于调度。

第 9 章的写时复制讨论用户态内存页。它不会把这里共享的内核打开文件描述变成两份独立偏移。两个进程也可能各有一个数值相同的 fd，却指向完全不同的对象；数值本身不能证明共享。

让引用关系决定读取结果

可逐步操作的教学模型；状态按下述规则计算，没有实际调用 Linux I/O。

    场景第一次读第二次读原因
    两个独立 opena 得到 fb 得到 f各有一个偏移。
    dup 后的两个描述符a 得到 fb 得到 o共同推进同一偏移。
    fork，子先读、父等待子得到 f父得到 o父子引用同一个打开文件描述。
    dup 后 close(a)a 不再有效b 仍可读 f移除一份引用不会关闭另一份。

    共享的后果可以沿一条线追踪

    查问题时，先从 fd 找打开文件描述，再问这份状态被谁引用。回到章节图的“共享位置 → 重定向”：dup2 正是修改描述符表（descriptor table）中的引用，让原有程序的输出走到另一个文件。
