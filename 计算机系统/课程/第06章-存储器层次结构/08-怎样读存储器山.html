先认三个轴，再看峰和坡

Size · 扫描范围

横跨 16 KiB 到 128 MiB。重复访问较小的工作集（working set），较容易在快缓存中复用。

Stride · 元素步长

本图一个元素是 8 B。s1 跨 8 B，s8 跨 64 B，不能把横轴数字直接看成字节。

高度 · 有效读取吞吐量

统计程序使用的数据量除以时间。不是把内存总线上搬运的所有字节都算入分子。

图中 32 KiB L1、256 KiB L2、8 MiB L3 和 64 B 块大小是该参考系统参数。曲面的数值来自教材测量，当前页面没有对你的电脑测速。

固定步长，沿工作集大小走

从右向左读：工作集由 16 KiB 增大，逐渐越过较快缓存的容量范围，主要供数层次发生变化，吞吐量（throughput）出现不同区段。这里每次跨 8 个 8 B 元素，正好是一个 64 B 块，因此块内空间复用很少。

这幅截面把“能否跨扫描保留工作集”的影响突出出来。它不说明缓存一到标称容量就一定整齐跳变：代码、其他数据、组映射等都可能占用或限制可用空间。

教材对 L2、L3 区域边缘的低谷没有给出确定原因，只提出可能与其他代码和数据造成的冲突有关。这些凹点的具体成因仍需进一步验证。

固定范围，增加步长：每次搬来的块用了多少？

教材图 6.43 固定范围 4 MiB，它放得下 L3，却超过 L2。一个 64 B 块含 8 个 8 B 元素。用一个不考虑预取的块利用率模型看：

元素步长每块约使用多少个元素每块有用数据比例
188/8 = 100%
244/8 = 50%
422/8 = 25%
811/8 = 12.5%

这些比例是伴读的规则步长算例，不是原图各点的精确吞吐比。步长达到一块或更大时，同次扫描几乎不再复用同块其他元素；再增加步长，曲线还可能受预取、地址映射和其他机制影响。

回看山图的小步长区域，教材把相对平坦的高吞吐脊线解释为硬件预取（hardware prefetching）的作用，并说明没有掌握算法细节。预取可以在实际读取之前装入数据，所以冷缓存手算模型与测量结果未必相同。

吞吐量不能直接当作一次 load 的延迟

读吞吐量 = 程序有效读取的字节数 / 耗时

伴读算例：读取 8 MiB 的有效数据，耗时 2 ms，得到 4,194,304,000 B/s，即约 4194 MB/s。MB/s 在这里采用十进制 10⁶ B/s；MiB 使用 2²⁰ B。

一个处理器可以同时保有多条在途读取。较高吞吐量与单条读取仍需等待多个周期可以同时成立，就像第 5 章区分功能单元的延迟与吞吐率那样。

因此，把 8 B 除以曲线高度得到的是平均供数间隔尺度，不能直接宣称“一个依赖 load 的实际延迟就是这么多”。依赖链与多个独立读取测到的侧面不同。

教材怎样测出这座山

图 6.40 的测试按不同 size 和 stride 扫描数组，使用 4 个累积器减轻单条加法依赖的限制，先预热，再计时。它把第 5 章的循环优化用于测量本章的存储系统。

理解测试时，先问：计入的是一次扫描还是重复扫描？数据预热了吗？size 是范围还是实际读取量？stride 是元素数还是字节数？这些条件决定曲线回答的是什么问题。
